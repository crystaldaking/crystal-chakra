# v0.2.0 Persistence Acceptance Evaluation (issue #38)

Date: 2026-08-29

This record answers issue #38: do persistent syntax facts beat deterministic
rebuilds by enough to justify cache complexity (SPEC §14)? It defines the
measurement harness, reports real numbers, and states the go/no-go budgets
issue #39 must satisfy. Graph restoration is deliberately **not** implemented;
the cache measured here is an honestly named synthetic model.

## Environment

- OS: Linux 6.18.33.2-microsoft-standard-WSL2, x86_64 (WSL2)
- CPU / memory: AMD Ryzen 7 9800X3D, 16 logical CPUs, 15 GiB
- Rust: pinned workspace toolchain (`1.97.1`)
- Profile: Cargo `release`
- Chakra branch: `feature/38-persistence-benchmarks`

## Method

New `chakra-conformance persistence` subcommand (evaluation tooling only; no
production crate changes). Per target it measures five phases per run:

1. **Cold rebuild** — `index_repository_with_options` from scratch.
2. **Cache write** — build a benchmark-local per-file projection from the
   public graph API (path, content hash, declarations, relationships
   including imports, diagnostic counts, call candidates; bounded per file
   with counted overflow) and serialize it as one JSON fact file per source
   file plus a `manifest.json` compatibility manifest.
3. **Warm restore** — check the compatibility key, hash every worktree source
   from disk, and read + deserialize every hit's fact file.
4. **Validation only** — compatibility key plus source hashes, no fact reads.
5. **One-file refresh** — append one probe declaration, restore the hits
   (exactly one miss), and reparse the miss through the public
   `scan_repository` + `reconcile_sources` path. The edit is always reverted
   and the checkout is verified clean.

The compatibility key follows SPEC §14: repository identity, commit SHA,
model index-format version, indexing-configuration fingerprint, and a content
fingerprint over all `(path, content_hash)` pairs. Parser/provider versions
are out of scope for this syntax-only model. A key mismatch is not an error:
restore reports incompatible and the caller falls back to a deterministic
rebuild (covered by hermetic tests).

Honesty limits of the model, by design:

- Restore covers read + validation + deserialization only; graph reassembly
  is excluded (issue scope), so every restore speedup below is an **upper
  bound**. Issue #39 must re-validate the gate with real reassembly cost.
- Content validation hashes every source file — the conservative model. A
  metadata-first cache would look cheaper than measured here.
- JSON is the model encoding. It bounds the size question from above; a
  production binary encoding must beat it (budget B4).
- Peak-RSS samples after the cold rebuild are process-cumulative, so restore
  RSS cannot be isolated inside one process (budget B6 is deferred to #39).
  Targets themselves run in isolated child processes, like the corpus runner.

Command (release-only; missing checkouts are skipped, never fetched):

```sh
cargo run --release --locked -p chakra-conformance -- persistence
```

Artifacts: `target/persistence/persistence-<target>.json` (schema version 1,
git-ignored). Two full suite invocations × two runs per target produced the
spread below; model-cache bytes were byte-identical across invocations.

Cross-check: symbols/edges/call-site counts and source bytes are identical to
the committed macOS corpus artifacts for all four repositories (e.g. symfony
122,685 / 245,871 / 254,783), so the measured revisions are reproducible
across platforms. Both PHP repositories carry the same four bounded
framework-extraction degradation records as the committed artifacts.

Run values are from the final suite invocation; ranges span all four
measurements (2 invocations × 2 runs). Hit ratio was 100% on every unchanged
restore, and every refresh produced exactly one miss and exactly one reparsed
file.

CPU (process user+system): cold rebuild is parallel — 4.3 s CPU for laravel,
13.4 s for symfony against 2.0 s / 4.9 s wall. Restore, validation, and write
are single-core: CPU ≈ wall on every target (symfony restore 0.345 s CPU for
0.345 s wall). Persistence therefore saves roughly 13 s of CPU per symfony
startup, not only wall time.

Cold-rebuild peak RSS (indexer phase sampler): 75 MiB ripgrep, 135 MiB tokio,
589 MiB laravel, 1.06–1.37 GiB symfony.

Refresh anatomy: the total is restore-of-hits plus reconcile. The reconcile
half is dominated by the full source scan, not by reparsing one file
(symfony: 336 ms restore + 583 ms reconcile; ripgrep: 10 ms + 216 ms). Below
roughly 1,000 files that fixed scan cost eats the entire win: ripgrep and
tokio refresh *slower than or equal to* a cold rebuild (0.6–1.1×), while
laravel reaches 5–9× and symfony 5–9× faster than rebuild.

Model-cache size: 2.2× source bytes (ripgrep), 2.0× (tokio), 3.9× (laravel),
1.6× (symfony). Relationship/call-candidate density, not source size, drives
the ratio.

## Go/no-go budgets for issue #39

Persistence is justified **only above a size gate**; below it the
deterministic rebuild is already fast and strictly simpler. Issue #39 accepts
or rejects a real implementation against these budgets, measured with the
same harness phases plus real graph reassembly:

- **B1 (restore gate, primary):** warm restore — including reassembly — must
  be **≥ 5× faster than cold rebuild wall** on repositories with **> 1,000
  indexed files**. Model evidence: 12–19× before reassembly. Below the gate
  persistence is off by default (observed: no refresh win under ~1,000
  files); if reassembly eats the margin below 5×, the answer is no-go.
- **B2 (validation overhead):** cache validation on an unchanged worktree
  must cost **≤ 5% of cold rebuild wall**. Model evidence: 0.6–1.7% on the
  corpus repositories (68 ms against 4.9 s for symfony).
- **B3 (refresh budget):** one-file refresh (validation + restore of hits +
  reparse of misses) must cost **≤ 25% of cold rebuild wall** above the gate
  and must reparse exactly the changed file set. Model evidence: 12–17%
  (laravel), 15–21% (symfony); exactly one miss, one reparsed file.
- **B4 (bytes budget):** persisted facts must fit **≤ 2× retained source
  bytes** in the production encoding. The JSON model measured 1.6–3.9×, so
  JSON is rejected as the production format; if a compact binary encoding
  cannot hold 2× on relationship-heavy PHP repositories, persistence is
  rejected on size.
- **B5 (correctness/hit ratio):** 100% hit ratio on an unchanged worktree,
  exactly one miss per one-file edit, and a full deterministic rebuild on any
  compatibility-key mismatch (repository identity, commit SHA, index format
  version, graph model version, indexing configuration fingerprint) or I/O
  error — never a partial or stale answer. Hermetic tests pin this behavior.
- **B6 (memory, enforced in #39):** warm-restore peak RSS must stay **below
  the cold-rebuild peak** measured by the indexer sampler, verified in a
  restore-only process; this harness records only process-cumulative samples
  after the rebuild.

## Deterministic rebuild fallback

The cache is always an optimization, never a requirement: miss,
incompatibility, corruption, or any doubt means running the same deterministic
rebuild measured here. Rebuild determinism is already enforced by the corpus
`fingerprint` scenario, and this evaluation adds cross-platform count equality
plus byte-identical model-cache writes across runs. Startup must never block
on, trust, or be corrupted by the cache; the fallback path is the default
path below the B1 size gate.

## Verdict

**Conditional go** for issue #39: build the real per-file persistence
prototype scoped to repositories above the B1 gate, with budgets B1–B6 as its
acceptance criteria and the deterministic rebuild as the universal fallback.
The model shows an order-of-magnitude margin on representative large
repositories (12–19× restore, 5–9× refresh, validation under 2%), large
enough to survive realistic reassembly and encoding overhead — but the
restore numbers are upper bounds by construction, and B1 must be re-measured
with real reassembly before the cache ships.

## Limitations

- Restore speedups exclude graph reassembly (issue scope); B1 is
  unenforceable until #39 prototypes it.
- Restore-phase RSS is not isolated (process-cumulative sampler); B6 defers
  the memory verdict to a restore-only process measurement.
- CPU samples use `RUSAGE_SELF`; Git inventory subprocesses are attributed
  only where the indexer already accounts for them.
- Model caches were written to a real disk (`target/tmp/persistence`), but
  WSL2 page-cache behavior may flatter read phases; the validation-only row
  bounds the pure hashing cost.
- The model hash is fixed-key SipHash-1-3, not a cryptographic hash; hit
  ratios and sizes are unaffected, a production key must not reuse it.
- Fixture repositories are tiny by design; they pin harness correctness
  (hermetic CI tests), not performance conclusions.
