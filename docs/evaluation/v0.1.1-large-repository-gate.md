# v0.1.1 Large-repository Gate

This protocol turns the Rust and PHP scale investigations into repeatable
release-build checks. The routine gate generates its repository in a temporary
directory, requires no network access, and leaves no evaluated source in this
repository.

## Routine generated gate

Run the same commands as CI:

```sh
cargo build --locked --release --workspace
cargo test --locked --release -p chakra-mcp \
  --test large_repository_gate \
  generated_multi_language_release_gate \
  -- --ignored --exact --nocapture
```

The generated Git worktree contains 98 Rust files, 96 PHP files, 2,300 callers
of one Rust function, and repeated ambiguous PHP method names. The test covers:

- cold indexing and an unchanged restart with identical graph fingerprints;
- complete Rust/PHP file coverage, every indexing phase, graph consistency,
  source/symbol/edge/call-site counts, scheduling and RSS observations;
- `allow_stale` query work separately from five deterministic
  `require_fresh` no-op reconciliations;
- a one-file relationship edit and an editor-style rename replacement, both
  followed by a fresh barrier and structural-publication checks;
- clean and changed `diff_context` timing;
- explicit PHP ambiguity, a high-degree caller work stop, cancellation before
  work, and degraded-provider syntax fallback;
- one in-process stdio MCP round trip, response size, serialization time and
  exact response-budget walk time.

Success prints one compact JSON object prefixed with
`CHAKRA_V0_1_1_GATE=`. The payload includes the Chakra commit, whether the
worktree was clean, build profile, full Rust toolchain description, OS,
architecture, logical concurrency, CPU model and physical memory. CI logs can
therefore be extracted without parsing human test output. The latest clean
local result summary is stored in
[`v0.1.1-large-repository-gate.json`](v0.1.1-large-repository-gate.json); the
CI line remains the complete serialized gate payload.

The routine thresholds are deliberately machine-tolerant regression rails,
not cross-machine service-level claims: cold start and unchanged restart must
each finish within 30 seconds; fresh barriers, edits, diff/provider queries and
the MCP round trip must each finish within 5 seconds; observed indexing RSS
must remain within the published 2 GiB target; and the structured MCP envelope
must remain within 1 MiB. Structural assertions are deterministic and do not
depend on those wall-clock thresholds.

Failures name the specific metric or violated invariant. Examples include
`cold_start_micros`, `observed_phase_peak_rss_bytes`,
`require_fresh_max_micros`, `changed_diff_micros`, and
`mcp_response_bytes`.

## Public full-size Rust evaluation

The public reference input is
`zed-industries/zed@bc538def4545534201bbfcac4e95ac34ea6501b6`.
Use a dedicated checkout and do not commit its sources or generated reports to
Chakra:

```sh
git clone https://github.com/zed-industries/zed.git /absolute/path/to/zed
git -C /absolute/path/to/zed checkout \
  bc538def4545534201bbfcac4e95ac34ea6501b6

CHAKRA_LARGE_REPOSITORY=/absolute/path/to/zed \
  cargo test --locked --release -p chakra-language \
  --test large_workspace -- --ignored --nocapture --test-threads=1
```

The ignored harness checks published budgets and phase measurements, compares
1/2/available-worker graph fingerprints, performs the structural one-file edit
inside an isolated shared clone, and measures ten warmed no-op fresh barriers.
`CHAKRA_INDEX_WORKERS=<n>` can pin the worker count for an additional run.

The public run is manual because cloning and repeatedly indexing Zed would make
ordinary pull-request CI slow and network-dependent. The generated gate is the
routine regression check; the pinned Zed run remains the comparable full-scale
release evaluation.

## Private PHP evaluation

The same ignored `large_workspace` harness accepts an absolute private Git
worktree through `CHAKRA_LARGE_REPOSITORY`. It reads the external worktree and
uses an isolated clone for the edit case. Record only aggregate metrics and
machine context; never copy private source, paths containing credentials, or
repository contents into Chakra.

## Reading the result

- `cold_start` and `unchanged_restart` contain coverage, scheduling, memory and
  per-phase metrics.
- `no_op_freshness` separates pure `allow_stale` latency from the authoritative
  Git/filesystem barrier, including separate source and Cargo/Composer metadata
  identity counts, source-body reads and Git subprocesses.
- `one_file_edit` and `editor_rename_replacement` expose reparsed and
  relationship-owner counts plus rebuilt/reused publication payloads.
  `copied_edges` is retained because replacing a touched high-degree adjacency
  vector may copy lightweight entries; source, symbol and call-site payloads
  must remain structurally shared.
- `queries` separates clean/changed diff, high-degree graph traversal,
  cancellation and degraded-provider timing/metadata.
- `mcp` separates end-to-end round-trip bytes/time from adapter serialization
  and exact budget checking.

The generated corpus is a regression instrument, not a claim that it models
all layouts in Zed or a production PHP application. Product conclusions should
combine this gate with the public full-size run and real agent evaluations.
