# v0.3.0 shared and prebuilt complete-snapshot evaluation (issue #50)

Date: 2026-09-02

This record evaluates whether the complete compatible commit snapshots from
issue #49 justify default local disk restore or a CI-produced artifact import
path. The verdict is **no-go for both**. Process-local sharing remains enabled;
the existing disk store remains opt-in, and no prebuilt-import surface is
added.

## Environment

- OS: macOS Darwin 25.6.0, arm64
- CPU / memory: Apple M4, 10 logical CPUs, 16 GiB
- Rust: pinned workspace toolchain (`1.97.1`)
- Profile: Cargo `release`
- Chakra base: `develop` at `4eece941c0ff902b4118c6bdf39fcee152a35c02`
- Corpus: the four pinned Rust/PHP revisions in
  `docs/support/corpus/manifest.json`

## Method

The release-only `chakra-conformance shared-indexes` command exercises the
production `CommitSnapshotCache` and `CommitIndexReport` codec; it is not a
synthetic cache model. Each target runs in an isolated process and each run
measures:

1. a deterministic cold commit build;
2. another cold build plus production snapshot encoding and atomic storage;
3. a fresh-cache local disk restore;
4. BLAKE3 verification, a byte-for-byte copy of the artifact triplet to a
   fresh cache root, and verification of the imported bytes; and
5. a fresh-cache restore of that copied prebuilt artifact.

The command never fetches repositories or artifacts. Missing, dirty, or
SHA-mismatched corpus checkouts are skipped rather than repaired. Machine
readable schema-1 reports are written under `target/shared-indexes/` and are
git-ignored.

Command:

```sh
cargo run --release --locked -p chakra-conformance -- \
  shared-indexes --no-fixtures --language rust --language php --runs 2
```

The fixed decision gates reuse the accepted v0.2 persistence budgets:

- only repositories with more than 1,000 indexed source files can qualify;
- complete restore must be at least 5× faster than a cold rebuild;
- the complete artifact must be no more than 2× retained source bytes; and
- both local and copied-artifact restores must exactly match the cold graph.

The graph check compares file/source counts, bytes, symbols, edges, call
sites, and a deterministic benchmark fingerprint. The production payload
also verifies its bounded envelope length and BLAKE3 checksum. The transport
digest covers the three named artifact files and is compared before import.

## Trust, provenance, and compatibility

A digest proves integrity, not who produced an artifact. The benchmark models
an artifact that has already arrived through a trusted CI channel; it does not
claim that a local BLAKE3 value authenticates CI. A future import design would
require an authenticated producer/channel plus explicit user opt-in, and its
provenance envelope would have to bind:

- producer identity and trust policy;
- Git-aware repository identity and exact commit;
- snapshot format, graph model, Chakra language-index version, every adapter
  snapshot version, and indexing-budget fingerprint;
- the materialization-independent commit-syntax fact scope; and
- the artifact digest and byte length.

The evaluated production compatibility key already contains the repository,
commit, format/model/language/adapter versions, and indexing configuration.
Any mismatch, corruption, I/O failure, or size violation rebuilds from Git.
The snapshot codec serializes commit syntax and incremental adapter state
only. Worktree overlays, provider inputs/processes, precise enrichment, and
other materialization-dependent facts are not eligible for transport.

Core operation remains network-independent: Git objects and the materialized
filesystem are canonical, and a local deterministic rebuild is always the
fallback.

## Results

Times and sizes below span the two final runs. `Speedup` is cold wall divided
by restore wall, so a value below 1× means restore is slower. Transport is the
local copy plus producer/import digest passes and is not included in prebuilt
restore time.

| Target | Files | Source | Cold | Artifact | Local restore | Prebuilt restore | Transport | Exact graph |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| ripgrep | 113 | 1.84 MiB | 144–148 ms | 19.2 MiB (10.39×) | 303–308 ms (0.48×) | 305 ms (0.47–0.48×) | 23–24 ms | yes |
| tokio | 793 | 5.42 MiB | 319 ms | 52.8 MiB (9.73×) | 830–842 ms (0.38×) | 830–837 ms (0.38×) | 62 ms | yes |
| laravel/framework | 3,047 | 17.26 MiB | 1.86–1.89 s | 284.6 MiB (16.49×) | 4.35–4.48 s (0.42–0.43×) | 4.42–4.52 s (0.41–0.43×) | 333–342 ms | yes |
| symfony/symfony | 11,142 | 87.17 MiB | 4.59–4.70 s | unavailable (>512 MiB writer bound) | unavailable | unavailable | unavailable | unavailable |

Fixture runs pin the end-to-end harness and copied-artifact path but are below
the decision gate. Ripgrep and tokio are also below the gate and are included
only to show scaling. Laravel and Symfony are the qualifying large targets.

Cold builds use parallel CPU effectively: Laravel consumed 5.05–5.20 s CPU
for 1.86–1.89 s wall, while local restore consumed 4.33–4.46 s CPU for
4.35–4.48 s wall. Symfony cold builds consumed 16.7–17.3 s CPU for
4.59–4.70 s wall. Complete decode/audit is single-core and does not remove
enough work to beat parallel parsing and graph construction.

Process high-water RSS is recorded for every phase, but it is monotonic within
a run: local/prebuilt phases follow two cold graphs and therefore cannot
isolate restore-only memory. No memory approval is inferred. The primary wall
and byte gates fail by margins large enough that a separate restore-only RSS
experiment cannot change the decision.

Symfony deterministically fails while the bounded MessagePack writer reaches
the 512 MiB limit. The initial evaluation exposed that this path was labeled
`corrupt` instead of `oversized`; issue #162 corrected the typed rejection
before the beta. The benchmark always treats the target as unavailable, never
as a successful restore, so the decision is unchanged.

## Gate outcomes

| Gate | Requirement | Laravel | Symfony | Verdict |
|---|---|---|---|---|
| Complete local restore | ≥5× faster | 0.43× | no artifact | **FAIL** |
| Complete prebuilt restore | ≥5× faster | 0.41–0.44× | no artifact | **FAIL** |
| Artifact size | ≤2× source | 16.49× | >5.87× before completion | **FAIL** |
| Exact restored graph | exact cold match | pass | not measurable | incomplete |
| Transport integrity | exact BLAKE3/bytes | pass | not measurable | incomplete |
| Provider isolation | no materialization-dependent facts | pass by codec contract | pass by codec contract | pass |
| Network independence | no service required | pass | pass | pass |

Artifact bytes differ across independent encodes because internal map
serialization order is not a reproducible-build contract. This does not
weaken per-artifact integrity: each transported artifact carries and verifies
its own digest, compatibility key, length, and payload checksum, and every
successful decoded graph matched the cold graph. A future distribution format
may require reproducible bytes, but this evaluation does not approve one.

## Decision

Default local disk restore and prebuilt import are rejected. On the only large
target that produces an artifact, restore is roughly 2.3–2.5× slower than
rebuild instead of 5× faster, and the artifact is 16.49× source instead of at
most 2×. The larger target cannot encode within the 512 MiB safety bound.
Transport itself is comparatively cheap, but it cannot compensate for decode,
merge, and consistency-audit cost.

Accordingly:

- process-local compatible snapshot sharing from issue #49 stays enabled;
- local disk artifacts remain an explicit opt-in experiment;
- Chakra gains no CI artifact import, network fetch, or default disk-cache
  configuration in v0.3.0; and
- any future proposal must change the representation or restore architecture
  and rerun these same complete-graph gates before product implementation.

## Limitations

- Corpus performance evidence covers Rust and PHP; both supported shapes
  below the size gate and both qualifying large PHP repositories were measured.
- The prebuilt path simulates an artifact already delivered through trusted
  CI. Network transfer and CI authentication are intentionally excluded; no
  production import exists to secure yet.
- Filesystem page-cache effects apply to local reads. Restore loses by more
  than 2× despite this favorable condition.
- RSS samples are process-cumulative as described above and do not constitute
  a restore-only memory verdict.
