# v0.2.0 incremental Tree-sitter parsing evaluation (issue #45)

Date: 2026-08-30

## Question

Chakra's syntax indexing currently reparses every changed file from source
with no retained parse state: `Parser::parse(source, None)` in every
per-language parser, and unchanged files are already skipped by exact content
comparison in the reconcile path. This evaluation determines whether retaining
one Tree-sitter tree per file and reparsing with `Tree::edit` +
`Parser::parse(new_source, Some(&old_tree))` improves common editor-edit
workloads enough to justify the retained memory and lifecycle cost.

The harness is benchmark-only code in `chakra-conformance`
(`src/incremental.rs`, `tests/incremental.rs`). No production parser,
driver, or reconcile code was changed for this evaluation.

## Predefined go/no-go thresholds

These thresholds were fixed before any measurement ran. Implement means a
minimal retained-tree integration into the reconcile path with tests; reject
means this document records the evidence and production code stays untouched.

- **T1 — fact exactness (hard gate).** The tree produced by `Tree::edit` +
  incremental parse must be structurally identical to a deterministic full
  reparse of the same source in 100% of comparisons: every timed scenario
  iteration and every randomized edit-sequence fuzz step, for every evaluated
  language. Structural identity is an exact, node-by-node full-cursor
  comparison over kind, byte/point range, child layout, and
  named/error/missing/extra flags. With identical source text these are the
  tree properties Chakra's deterministic extraction passes observe, so
  structural equality implies extracted-fact equality. Any mismatch is an
  automatic no-go.
- **T2 — small-edit speed.** Median incremental wall time for a one-token
  edit must be at most 1/3 of the full-reparse median (≥3× faster) for at
  least 4 of the 5 evaluated languages on representative medium files
  (roughly 20–200 KiB of real corpus code).
- **T3 — large-file speed.** The same ≥3× bound must hold for a one-token
  edit in the largest evaluated corpus file of each available language
  (files ≥300 KiB where the corpus provides one).
- **T4 — atomic-replace regression bound.** When the whole file is replaced
  (tree reuse cannot help), incremental-with-edit bookkeeping must not be
  slower than 1.25× the full-reparse median.
- **T5 — retained memory.** Retained trees must cost at most 5× the retained
  source bytes of the same file set, measured as resident-set delta over a
  whole per-language corpus file set.
- **T6 — cancellation.** Incremental parse must not be materially harder to
  interrupt: median cancellation latency (cancel signal to parse return via
  the tree-sitter 0.26 progress callback) must stay within 1.25× of the
  full-parse latency.

All of T1–T6 must pass for a go verdict. If any threshold fails, the verdict
is no-go with the failing evidence recorded below.

## Method

Per language and document, both arms start from the same freshly parsed base
tree:

- **full**: `Parser::parse(new_source, None)` — exactly what production does
  per changed file today (the production parsers additionally run Chakra's
  extraction passes; those passes are byte-identical work in both arms, so
  the measured delta is the Tree-sitter parse cost the issue asks about).
- **incremental**: apply the text edit to the retained tree via
  `Tree::edit(InputEdit)` and reparse with
  `Parser::parse(new_source, Some(&edited_tree))`; the retained tree is then
  replaced by the result, modeling one retained tree per file. `Tree::edit`
  bookkeeping is included in the measured incremental cost.

Scenarios: `cold` (fresh parse baseline), `small-edit` (one-identifier
replacement, stepping through distinct deterministic positions),
`syntax-error` (alternating break/fix of one mid-file statement),
`atomic-replace` (alternating full-content swap between two real files of the
same language), `large-file-edit` (the `small-edit` scenario against the two
largest corpus files per language). `rename-delete` is not a timing race:
delete costs no parse, and rename with unchanged content is already free in
the reconcile path by exact content comparison; recreate pays a full parse in
both strategies because a retained tree cannot cross paths without a
content-hash lookup Chakra does not have. See Limitations.

Every timed scenario is replayed in a separate untimed validation pass that
compares the incremental and full trees node by node after each edit. Keeping
the exact comparison outside both timed arms prevents the correctness gate
from contaminating either sample. A separate seeded randomized fuzz applies
long sequences of random identifier replacements, deletions, and insertions
(including one non-ASCII token), performing the same exact comparison at
every step.

CPU time is sampled with `getrusage` deltas around each measured block (the
parse loop is single-threaded, so CPU ≈ wall, visible in the tables). Memory
is the `VmRSS` resident-set delta of retaining one tree per file for a whole
per-language corpus set after an allocator warm-up pass. Cancellation uses
the tree-sitter 0.26 `ParseOptions::progress_callback` returning
`ControlFlow::Break` once a background thread trips an atomic flag; the
signal delay is self-calibrated per arm to one quarter of that arm's
uncancelled parse time (clamped to ≥20 µs), because the arms differ by
orders of magnitude. Both arms parse the same text — the document with one
mid-file broken snippet, modeling a file mid-typing. Chakra's production
parsers install no parser-level callback today (reconcile cancels between
files), so T6 compares interruptibility of the two strategies, not a
regression against shipped behavior.

Commands (release, already-compiled):

```sh
cargo test --locked --release -p chakra-conformance --test incremental \
  bench_corpus_documents -- --ignored --exact --nocapture
cargo test --locked --release -p chakra-conformance --test incremental \
  bench_hermetic_documents -- --ignored --exact --nocapture
for lang in rust php go python typescript; do
  CHAKRA_INCREMENTAL_BENCH_LANGUAGE=$lang \
    cargo test --locked --release -p chakra-conformance --test incremental \
    bench_retained_memory -- --ignored --exact --nocapture
  CHAKRA_INCREMENTAL_BENCH_LANGUAGE=$lang \
    cargo test --locked --release -p chakra-conformance --test incremental \
    bench_cancellation_latency -- --ignored --exact --nocapture
done
```

### Threshold evaluation

- **T1 fact exactness: PASS.** Zero divergences in ~2,970 comparisons,
  including error-recovery trees.
- **T2 small-edit speed: PASS.** Corpus medium files: 13.4–99.4× per language
  (rust 24–57×, php 13–57×, go 28–99×, python 18–55×, typescript 34–76×),
  all five languages far above 3×.
- **T3 large-file speed: PASS for code files, with a caveat.** 30–363× on
  real code up to 3.9 MiB. The byte-largest evaluated TypeScript and second
  PHP files are giant single-literal data fixtures where nothing can be
  reused (1.0×); the largest real-code TypeScript file (vscode.d.ts,
  725 KiB) reaches 59.4×.
- **T4 atomic-replace bound: FAIL.** Whole-file replacement with edit
  bookkeeping is slower than a full reparse for rust (1.76×), php (2.49×),
  and go (1.30×); python (1.18×) and typescript (1.005×) stay inside the
  bound. The alternation is adversarial by design (each arm starts from the
  other document's edited tree), and the overhead is the failed reuse
  analysis itself.
- **T5 retained memory: FAIL.** 22.6–36.0 tree bytes per source byte against
  a 5× budget, on all five languages.
- **T6 cancellation: MIXED.** Abort latency is microseconds for both arms
  whenever the parser can observe the flag; strict ratios fail for
  rust/php/python at that scale, pass for Go, and the two TypeScript arms are
  effectively equal at ~5.9 ms while lexing one giant token. There is no
  material strategy regression, but no clean threshold pass either.

## Verdict

**No-go: retained Tree-sitter trees are rejected for the reconcile path.**

Two of six predefined thresholds fail, including both cost-side gates:

1. **T5 (retained memory) fails decisively.** Retaining one tree per file
   costs 22.6–36.0 bytes per source byte — roughly 1.0–1.25 GiB for a
   ~45 MiB-source workspace, exceeding the entire current index peak RSS of
   the largest previously benchmarked repository. No plausible gain on
   save-driven edits justifies multiplying Chakra's resident footprint by
   that factor.
2. **T4 (atomic-replace) fails for 3 of 5 languages.** Whole-file
   replacement (checkouts, formatter rewrites, generated-code refresh) is
   1.3–2.5× slower with edit bookkeeping than a plain reparse, so retained
   trees would actively regress non-editor workloads unless a size-gated
   reuse policy were added — more machinery, against the
   no-cache-complexity-before-benchmarks invariant.

The speed side is real: T2/T3 pass by an order of magnitude (10–360× on the
edits that dominate editor workflows), and T1 shows the incremental trees
are fact-exact. The benefit is simply aimed at a workload Chakra does not
have: Chakra reconciles on watcher/save events, where a changed medium file
already reparses in 0.8–13 ms and unchanged files are already free. The
rejected design's cost is continuous (memory held for every indexed file);
its benefit is bounded by how often sub-13 ms reparses matter to an agent
query surface that already pays graph validation and materialization on the
same path.

The harness, fuzz gate, and this document are the rejection evidence. A
revisit is justified only if a future profile shows Tree-sitter parsing
dominating reconcile wall time on real workloads; any such retry should
evaluate a bounded, size-gated tree cache (small edits only, memory-budgeted)
rather than one retained tree per file.

## Limitations

- Edit sites are identifier-token replacements chosen deterministically.
  Edits that break the root structure (the `emoji-sat.php` 1.0× row) are
  realistic but over-represented in data files with few identifier sites;
  both outcomes are reported.
- Memory deltas are process `VmRSS` deltas after a warm-up pass; allocator
  retention makes them approximate, but a 23–36× ratio is far outside any
  plausible measurement error.
- Cancellation is observed through the tree-sitter progress callback, which
  fires every ~100 parse operations; parses shorter than that complete
  before observation, and one giant token (the TypeScript data fixture)
  blocks observation for ~5.9 ms in both arms.
- `rename-delete` has no incremental race to run: delete and
  content-identical rename are already free in the reconcile path, and a
  rename with changed content cannot reuse a tree across paths without a
  content-hash lookup that does not exist.
- Results are from one machine (Ryzen 9800X3D, WSL2); absolute numbers will
  vary, ratios are the evidence.
