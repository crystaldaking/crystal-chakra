# v0.2.0 syntax fact cache acceptance evaluation (issue #39)

Date: 2026-08-29

This record applies the B1–B6 budgets defined by
`docs/evaluation/v0.2.0-persistence-acceptance.md` to a real per-file syntax
fact cache prototype. The verdict is **no-go**. The prototype is preserved in
PR #136 as measurement evidence, but its production cache code and dependency
are deliberately not part of v0.2.0.

## Prototype under test

The prototype stored materialization-independent declarations, syntax
relations, call candidates, diagnostics, content hashes, and extractor/model
versions in a bounded binary format. It did not persist source text,
revision-local entity ids, or precise live-provider facts. Restore validated
the compatibility key and per-file hashes, decoded facts, rebuilt the graph
through the normal bounded materialization pipeline, ran the full consistency
audit, and compared the result with a deterministic cold rebuild.

Corrupt, truncated, missing, oversized, or incompatible data fell back to
parsing. Writes used temporary files plus rename with the manifest as commit
point. These properties were covered by hermetic tests on the prototype
branch; they establish that the experiment was correct enough to measure,
not that the rejected format is a supported Chakra contract.

## Method

The release-profile command on the prototype branch was:

```sh
cargo run --release --locked -p chakra-conformance -- persistence --real
```

Each target measured:

1. deterministic cold rebuild;
2. cache write;
3. unchanged warm restore including validation, decode, graph reassembly,
   merge, consistency audit, and fingerprint comparison;
4. marginal compatibility/hash validation;
5. one-file refresh with exactly one expected miss and a cold-rebuild
   fingerprint comparison;
6. restore-only peak RSS in a separate process.

The environment was Linux 6.18 under WSL2 on an AMD Ryzen 7 9800X3D (16
logical CPUs, 15 GiB memory), using the pinned Rust 1.97.1 toolchain. The
corpus revisions were the same pinned Rust/PHP repositories used by the
issue #38 harness.

## Results

| Target | Files | Source | Cold rebuild | Cache bytes | Warm restore | Speedup | Validation | One-file refresh |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| ripgrep | 113 | 1.8 MiB | 0.13–0.14 s | cache disabled below gate | — | — | — | — |
| tokio | 793 | 5.4 MiB | 0.31–0.34 s | cache disabled below gate | — | — | — | — |
| laravel/framework | 3,047 | 17.3 MiB | 1.78–2.01 s | 12.34 MB (0.68×) | 1.43–1.82 s | **1.10–1.24×** | 16–17 ms | 1.59–1.95 s (79–97%) |
| symfony/symfony | 11,140 | 87.2 MiB | 4.43–5.02 s | 29.92 MB (0.33×) | 3.36–4.27 s | **1.16–1.33×** | 42–44 ms | 3.82–4.65 s (83–93%) |

Unchanged restores had 100% hit ratio. A one-file edit produced exactly one
miss and one reparse. Every restored/refreshed graph fingerprint matched a
deterministic rebuild.

The restore bottleneck was structural: graph materialization plus the
mandatory consistency audit consumed 83–86% of restore wall time. Those
phases also account for roughly 40–50% of a cold rebuild, while parsing—the
only work removed by the fact cache—is the other half. Encoding and I/O work
cannot turn that architecture into the required 5× speedup.

## Budget outcomes

| Budget | Requirement | Measured | Verdict |
|---|---|---|---|
| B1 restore | ≥5× faster than cold above 1,000 files | 1.10–1.33× | **FAIL** |
| B2 validation | ≤5% of cold wall | 0.8–0.9% | PASS |
| B3 refresh | ≤25% of cold wall; exact changed set | 79–97%; exact one-file miss | **FAIL** |
| B4 bytes | ≤2× retained source | 0.33–0.68× | PASS |
| B5 correctness | exact hits/fallback/fingerprint behavior | held in all runs | PASS |
| B6 memory | restore peak below cold peak | held in 3 of 4 above-gate runs | MARGINAL |

Restore-only peak RSS was stable at 560–561 MiB for Laravel and
1.183–1.184 GiB for Symfony. Cold-rebuild samples were allocator-sensitive;
one Symfony run put restore 7% above the low cold sample, so B6 was not
consistently satisfied.

## Decision

The cache fails the primary B1 gate and the B3 refresh budget by wide margins.
Per SPEC §14, its complexity is not justified, so v0.2.0 ships no syntax fact
cache, cache format, restore path, or cache hashing dependency. Machine-readable
diagnostics report the cache as disabled and do not fabricate version,
hit/miss, or corruption counters.

A future startup optimization should evaluate persistent graph snapshots,
which could avoid re-materialization rather than only parsing. That work is
outside v0.2.0 and requires its own architecture and compatibility decision.
Any future per-file-cache attempt must rerun B1–B6 with real graph assembly
and consistency validation included.

## Limitations

- Measurements were made on WSL2 with ordinary page-cache effects. The B1/B3
  failure margins are much larger than the observed run-to-run variance.
- The corpus covers Rust and PHP. Other language adapters were tested
  hermetically on the prototype but not benchmarked on public repositories.
- Prototype artifacts under `target/persistence/` are git-ignored and are not
  release assets; the table above is the durable decision record.
