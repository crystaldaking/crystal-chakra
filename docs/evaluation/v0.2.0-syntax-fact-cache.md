# v0.2.0 Syntax Fact Cache Acceptance Evaluation (issue #39)

Date: 2026-08-29

This record answers issue #39 against the go/no-go budgets B1–B6 defined in
`docs/evaluation/v0.2.0-persistence-acceptance.md` (issue #38). The
production per-file syntax fact cache in `chakra-language::cache` is
measured with real graph reassembly on the pinned corpus repositories. The
verdict is **no-go for the restore gate**: with honest reassembly through
the bounded build pipeline, warm restore reaches only 1.1–1.3× against the
cold rebuild, far below the required 5×. The cache implementation itself is
correct, bounded, and fingerprint-equivalent to deterministic rebuilds; it
ships opt-in and disabled by default.

## Environment

- OS: Linux 6.18.33.2-microsoft-standard-WSL2, x86_64 (WSL2)
- CPU / memory: AMD Ryzen 7 9800X3D, 16 logical CPUs, 15 GiB
- Rust: pinned workspace toolchain (`1.97.1`)
- Profile: Cargo `release`
- Chakra branch: `feature/39-syntax-fact-cache` (stacked on
  `feature/38-persistence-benchmarks`)

## Implementation under test

- **Schema.** `FileSyntaxFacts` mirrors the adapters' parser drafts:
  declarations (key fields, location, signature, parent index), call
  candidates (including PHP receiver types and the C++ promotion marker),
  named/typed relation drafts, Rust impl drafts, diagnostics, and content
  hashes. Entity ids are never stored (revision-scoped by design, ADR-0033);
  source text is never stored (re-read from the worktree during validation);
  precise live-provider facts are never stored (provenance tiers are
  recomputed during materialization, never persisted as upgraded truth).
- **Encoding.** Compact binary: LEB128 varints, one-byte enum tags, per-file
  string table, source ranges without the implied file path, BLAKE3-128
  checksum and explicit `INDEX_FORMAT_VERSION` per payload. JSON is not
  used anywhere in the production format (budget B4).
- **Compatibility key (SPEC §14).** Repository identity, HEAD commit,
  `INDEX_FORMAT_VERSION`, `GRAPH_MODEL_VERSION`, per-language extractor
  versions, the `chakra-language` crate version, and the indexing
  configuration fingerprint. Per-file content hashes (BLAKE3-128, not the
  model's fixed-key SipHash) gate freshness per file.
- **Restore path.** Scan (shared with the cold path) → key check → per-file
  hash validation → per-language rebuild from facts through the *same*
  bounded pipeline (`assemble`: catalog, relationships, bounded graph
  materialization) that cold builds use after parsing → merge → full
  consistency audit → the same atomic publication path. Misses are reparsed
  inside the same call. Fallbacks: corrupt/truncated fact file → reparse
  exactly that file; missing/corrupt/oversized/incompatible manifest →
  deterministic rebuild; adapter restore error → deterministic build of that
  partition. Publication of the cache itself is atomic (temporary file plus
  rename, manifest last), incremental (unchanged payloads reused), and
  bounded (entries, entry bytes, total bytes).

## Method

`chakra-conformance persistence --real` extends the issue #38 harness with
per run:

1. **Cold rebuild** — `index_repository_with_options` with the cache
   disabled (baseline), with the indexer phase RSS sampler.
2. **Cache write** — the same call with the cache enabled on an empty
   directory (build plus atomic publication), recording entries, bytes, and
   the B4 ratio against retained source bytes.
3. **Warm restore** — the same call on the populated cache, including
   validation, fact reads, reassembly, merge, audit, and publication. The
   restored graph's fingerprint (file summaries, symbols, edges, call
   sites) must equal the cold rebuild's.
4. **Validation only** — key resolution, manifest read, and content hashing
   with the scan timed separately: the scan is shared by the cold and
   restore paths, so B2 applies to the marginal cache-validation cost.
5. **One-file refresh** — one appended declaration; the cache-enabled call
   restores the hits and reparses exactly the edited file, verified against
   a deterministic rebuild of the edited tree; the edit is reverted and the
   checkout verified clean.
6. **Restore-only child (B6)** — a separate process restores the cache and
   reports its indexer peak RSS, so the restore peak is not inflated by a
   cold rebuild in the same process.

Command:

```sh
cargo run --release --locked -p chakra-conformance -- persistence --real
```

Artifacts: `target/persistence/persistence-real-<target>.json`
(`chakra.persistence-real` schema version 1, git-ignored). Results below
are from the final clean suite plus one repeated symfony suite (four
symfony runs total); spread is shown where it matters.

Restore phase anatomy (single illustrative run; the rest of the wall is
scan, hashing, and fact reads):

| Phase | laravel | symfony |
|---|---:|---:|
| Git inventory + source read | 47 ms | 217 ms |
| Symbol catalog + relationships | 28 ms | 59 ms |
| Graph materialization (bounded builder) | 689 ms | 1,759 ms |
| Consistency audit | 515 ms | 1,147 ms |
| Hash + fact read + decode (unphased) | ~120 ms | ~250 ms |

Materialization plus the mandatory consistency audit are 83–86% of the
restore wall. They are also 40–50% of the *cold* rebuild wall: Tree-sitter
parsing — the only work the cache eliminates — is the other half. This
caps the achievable restore speedup at roughly 2× with this architecture,
independent of encoding or I/O wins.

Correctness (B5): 100% hit ratio on every unchanged restore (3,047/3,047
and 11,140/11,140), exactly one miss per one-file edit, restored and
refreshed graph fingerprints identical to deterministic rebuilds on every
run. Skipped entries: zero. Below-gate repositories demonstrably keep the
cache off (no manifest written), which is the production default.

Memory (B6): the restore-only child peak RSS is deterministic across runs
(560–561 MiB laravel, 1.183–1.184 GiB symfony). The cold-rebuild indexer
sampler is not: laravel 596 MiB and 2.04 GiB, symfony 1.10–1.11 GiB and
4.41–4.42 GiB across runs (glibc arena high-water under parallel parsing,
not Chakra allocations; the issue #38 baseline recorded 1.06–1.37 GiB for
symfony). The strict comparison holds on 3 of 4 above-gate runs; on one
symfony run the restore peak (1.183 GiB) exceeded the cold sampler's low
band (1.104 GiB) by 7%.

## Budget outcomes

| Budget | Requirement | Measured | Verdict |
|---|---|---|---|
| B1 (restore gate) | restore ≥ 5× cold wall above 1,000 files | 1.10–1.24× (laravel), 1.16–1.33× (symfony) | **FAIL (no-go)** |
| B2 (validation) | ≤ 5% of cold wall | 0.8–0.9% marginal (scan shared and reported separately) | **PASS** |
| B3 (refresh) | ≤ 25% of cold wall, exactly the changed file set reparsed | 79–97% (laravel), 83–93% (symfony); exactly one miss, one reparsed file | **FAIL (no-go)** |
| B4 (bytes) | ≤ 2× retained source bytes | 0.68× (laravel), 0.33× (symfony) | **PASS** |
| B5 (correctness) | 100% hits unchanged, one miss per edit, rebuild on key mismatch | held on every run; hermetic tests pin the fallback matrix | **PASS** |
| B6 (memory) | restore-only peak RSS below the cold-rebuild peak | holds 3/4 above-gate runs; one symfony run 1.183 vs 1.104 GiB (+7%); restore peak stable, cold sampler volatile | **marginal — not consistently satisfied** |

## Verdict

**No-go for the restore gate (B1) and the refresh budget (B3).** The issue
#38 conditional-go warned that the model's 12–19× restore numbers excluded
reassembly; measured honestly, reassembly through the public bounded
builder plus the mandatory consistency audit costs about as much as the
parsing it replaces, capping warm restore at ~1.1–1.3×. Budgets B2, B4,
and B5 pass cleanly; B6 is marginal against a volatile cold-RSS sampler
(restore peak RSS is deterministic and inside the cold rebuild's typical
band, but the strict per-run comparison does not hold on every run).

Consequences:

- The cache stays **opt-in and disabled by default**, including below the
  1,000-file gate. The implementation is retained: it is correct
  (fingerprint-equivalent restores, isolated per-file fallback), bounded,
  atomic, and cheap on disk (0.33–0.68× source bytes), and it is the
  measurement substrate for any future re-attempt.
- Reaching B1 requires eliminating re-materialization from the restore
  path — persistent graph snapshots (deferred roadmap work), not a per-file
  fact cache. Skipping the consistency audit on restore was evaluated and
  rejected: it saves ~0.5 s (laravel) / ~1.1 s (symfony), which still
  leaves restore at ~2×, and it would weaken the publication guarantee
  ("publication still constructs and validates a private atomic revision").
- Any future re-attempt must re-run this harness; B1 is only enforceable
  with real reassembly, which is exactly what the model could not measure.

## Limitations

- Wall times are WSL2 measurements with page-cache warm-up between phases;
  run-to-run cold-rebuild spread is ±15% (symfony 4.43–5.02 s across
  suites). The B1/B3 margins are far larger than this noise; the verdicts
  are unaffected.
- The cold-rebuild peak-RSS sampler is process-cumulative and
  allocator-sensitive (1.1–4.4 GiB for identical work); B6 should be
  re-measured with per-phase RSS sampling if it becomes the deciding
  budget.
- The corpus covers Rust and PHP; the other nine languages share the same
  restore machinery (hermetic tests cover the shared driver, Rust, PHP, and
  C# families) but are not benchmarked here.
- The compatibility key includes the HEAD commit, so any commit invalidates
  the whole cache even when sources are unchanged (B5 as specified). A
  softer policy (per-file hash acceptance across commits) is a deliberate
  follow-up decision, not an oversight.
