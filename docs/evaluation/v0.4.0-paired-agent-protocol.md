# Chakra v0.4.0 paired agent-evaluation protocol

Status: accepted as the evaluation protocol for milestone v0.4.0 (issue #189).
Feeds: #190 (paired runs and go/no-go decision), #195 (release gate).
Supersedes for v0.4.0 purposes: `docs/evaluation/v0.1-template.md` (kept as
historical v0.1 worksheet).

## 1. Purpose

Measure, from recorded evidence rather than feature intuition, whether Chakra
improves real coding-agent outcomes before v0.4.0 expands the public query
surface. The protocol defines the corpus, the task catalog, the paired
conditions, the metrics, and the pre-registered decision rules for:

1. overall v0.4.0 scope direction, and
2. whether a standalone bounded `impact` query proceeds to specification
   (#191) and implementation (#192–#194).

Success and correctness take precedence over tool-call or token reductions.
The protocol distinguishes measured evidence from reviewer judgment, and no
general product claim may be drawn from a single repository or an anecdotal
run.

## 2. Corpus selection authority

`docs/evaluation/v0.4.0-paired/corpus.json` is the task and repository
authority for this evaluation. Its repository pins reuse
`docs/support/corpus/manifest.json` (ADR-0029): immutable commit SHAs, recorded
licenses, and local-evaluation-only use. Sources are never redistributed as
fixtures; all selected licenses permit local evaluation use.

Selected ecosystems and repositories:

| Ecosystem | Repository | Pinned SHA | Role |
| --- | --- | --- | --- |
| Rust | tokio-rs/tokio | `625954f365727668cb02d04172b34f1149637728` | Async workspace-of-crates; scheduler internals |
| Rust | BurntSushi/ripgrep | `3fce3b5bb0236da2df6d99672afb8a719642eca7` | Single-binary CLI; large integration test suite |
| PHP | laravel/framework | `faf45dd2b1549ff451993e9b20047ff0bf093033` | Large framework; deep cross-component call surfaces |
| Python | django/django | `d92b0209014021350af0383983315bf0a05ffac0` | Mature framework; extensive in-tree test suite |
| Go | prometheus/prometheus | `98c983239715d0d81b8acf3560d47aba2a6d1649` | Large application; PromQL engine and tests |

This covers four language ecosystems (more than the required three), including
Rust and PHP, with both library and application shapes. Every expected file and
test path in `corpus.json` was verified against the pinned SHA via the GitHub
tree API on 2026-09-11; a verification failure must be fixed in `corpus.json`
before any run that references the path.

## 3. Task catalog and scenario types

The catalog contains ten tasks: two per repository, plus the stale-worktree
scenario once on tokio and once on laravel/framework. Every task definition in
`corpus.json` records its brief, expected relevant files, expected related
tests, required validation, objective success criteria, and budgets **before
any run**. Changing a task after the first run of that task invalidates the
comparison and must be recorded as a protocol deviation in #190.

Scenario types, each exercised by at least two tasks:

- **navigation** — trace an execution path through unfamiliar code and report
  it with exact file/symbol references. Exercises `repo_map`, `search`,
  `symbol_search`, `context`.
- **change-surface discovery** — enumerate every in-repository caller,
  forwarder, overrider, and behavior-pinning test for a planned change.
  Exercises `symbol_search`, `context`, `callers`.
- **regression-test discovery** — identify the existing automated tests that
  would catch a regression for a planned refactor, and the modules under test.
  Exercises `repo_map`, `search`, `symbol_search`, `callers`.
- **stale-worktree** — the harness mutates one worktree file after setup and
  before the agent's final patch; the agent must detect drift and base its
  patch on the post-mutation state. Exercises `diff_context` and the freshness
  model. The mutation, its timestamp, and the post-mutation blob are recorded
  in the run manifest.

## 4. Paired conditions and controls

Each task runs twice with isolated fresh sessions:

- **baseline** — the agent has no access to Chakra. Before the run, verify
  Chakra is unreachable (no MCP server registered for the task worktree) and
  record the check.
- **chakra** — the same agent with the Chakra MCP server registered for the
  task worktree. Before the run, record a successful `status` result including
  revision, freshness, and provider state.

Held identical across both conditions:

- agent product and version, model, reasoning settings;
- client and permission/tool-approval policy;
- the repository worktree at the pinned starting revision;
- the task brief verbatim, including its success criteria;
- the wall-time and turn budgets from `corpus.json`;
- the machine and OS.

Record per evaluation session in `environment.json`: agent, model, reasoning
level, client version, permission policy, machine class/OS, Chakra version and
build commit, provider availability per language, and cache state. Paths must
be repository-relative; no secrets, tokens, usernames, or absolute machine
paths in any committed artifact.

### 4.1 Run order

Run order is counterbalanced: for each task, order is assigned by a seeded
shuffle (`baseline, chakra` vs `chakra, baseline`) with the seed recorded in
the run manifest, so the assignment is reproducible and reviewable. Across the
ten tasks the protocol targets five tasks per order; if a failed run unbalances
this, record the imbalance in #190 rather than silently re-running.

### 4.2 Cache and provider handling

- A repository's first Chakra run in a session may be a cold index; record
  `cache_state: cold | warm` per run. Do not artificially alternate cold/warm;
  report both and analyze cold and warm separately.
- Record language-server provider availability (installed, version, ready /
  catching-up / degraded / disabled) at run start and end. A Chakra run with an
  unavailable or degraded provider is still a valid run — honest fallback is a
  product feature — but the provider state must be in the manifest.
- A run whose setup check fails (baseline reachable Chakra, or missing Chakra
  `status`) is void, not failed: fix the setup and repeat with the same order
  assignment.

### 4.3 Failed and inconclusive runs

A run is **failed** when the agent exceeds budget, crashes, or stops without a
final artifact. One retry is permitted per task/condition with the failure
reason recorded; a second failure stands and is analyzed, not silently
excluded. A run is **inconclusive** when its correctness evidence cannot be
checked (for example the validation command cannot run in the evaluation
environment); inconclusive pairs are analyzed for why and excluded only from
the quantitative gates, never from the written report.

## 5. Metrics

Recorded per run, in `run.json` per
`docs/evaluation/v0.4.0-paired/run-result.schema.json`:

- **correctness** — outcome `success | partial | failure` against the task's
  objective criteria, with checkable evidence (diff, test output, or answer
  review against the expected file/test lists);
- **wall time** and **turns**;
- **search / read / shell call counts** — plus, in the Chakra condition,
  per-tool Chakra call counts (`repo_map`, `search`, `symbol_search`,
  `context`, `callers`, `diff_context`, `status`);
- **context tokens** (input) where the client makes them observable; where not
  observable, record `observable: false` and do not estimate;
- **relevant files and tests found / missed** against the task's expected
  lists;
- **stale-context incidents** — moments where the agent acted on outdated
  repository state, with whether and how the drift was detected;
- in the Chakra condition: initial and final `status` (revision, freshness,
  provider state), and counts of `truncated`, `catching_up`, and `degraded`
  responses.

Where a client does not expose a signal, record it as unobservable; do not
back-fill from memory.

## 6. Correctness scoring

Scoring order is fixed: correctness first, then discovery completeness, then
efficiency.

- **success** — every objective criterion in the task definition is met and
  the required validation passes or is review-confirmed;
- **partial** — the core question is answered but at least one objective
  criterion is missed, or validation is incomplete;
- **failure** — wrong, missing, or budget-exhausted outcome.

For quantitative summaries a `success` scores 1.0, `partial` 0.5, `failure`
0.0. Reviewer judgment (answer quality, noise, misleading output) is recorded
separately in the `reviewer` section of `run.json` and must never override the
objective outcome.

## 7. Pre-registered decision rules

These rules are fixed before the first run. Any change after runs begin is a
protocol deviation and must be recorded in #190 with rationale.

### 7.1 Overall v0.4.0 scope direction

Let `S_b`, `S_c` be mean correctness scores across analyzed pairs, and let
`E_nav/cs` be the median per-task reduction (baseline minus Chakra) in
search/read/shell calls across navigation and change-surface tasks.

- **Support expansion** when `S_c >= S_b` **and** (`E_nav/cs >= 30%` **or**
  median wall-time reduction `>= 25%` on the same task classes) **or**
  reviewers document at least two tasks where Chakra facts directly prevented
  a wrong inference.
- **Hold scope and fix** when `S_c < S_b`, or when degraded/truncated responses
  materially drove failures — file defects first per the dogfooding rule.
- **Inconclusive** when fewer than seven pairs are analyzable; extend the
  corpus rather than lowering the bar.

### 7.2 Standalone `impact` query go/no-go

Go requires **all** of:

1. **Correctness gate** — `S_c >= S_b` (no correctness regression).
2. **Unmet-need gate** — reviewers identify at least one repeated user problem
   across runs that the existing `context` and `diff_context` tools demonstrably
   do not solve well, with run-manifest references.
3. **Bounded-value hypothesis** — the recorded evidence supports a specific
   minimum capability statement (what `impact` must answer, for whom, and how
   much of the observed gap it plausibly closes), written into #191.

If any gate fails, record no-go in #190, close or rescope #191–#194 with
rationale, and redefine the milestone before any release-branch or version-bump
work (#195).

## 8. Artifacts and storage

- One `run.json` per run at
  `docs/evaluation/v0.4.0-paired/runs/<task_id>/<condition>/run.json`,
  validated against `run-result.schema.json`.
- Raw transcripts, diffs, and tool logs referenced by repository-relative
  paths under the same run directory; large logs may be gzipped.
- One `environment.json` per evaluation session in
  `docs/evaluation/v0.4.0-paired/runs/`, referenced from every run it covers.
- The paired analysis and the written go/no-go decision are committed as
  `docs/evaluation/v0.4.0-paired/ANALYSIS.md` by #190.
- Never commit secrets, tokens, absolute machine paths, or corpus source code.

## 9. Reproduction

1. Fetch the corpus checkouts: `python3 tools/fetch_corpus.py` (opt-in,
   pinned-SHA shallow checkouts under `target/corpus/`; verify HEAD matches
   `corpus.json`).
2. For edit tasks, copy the pinned checkout to a scratch worktree; restore the
   pinned SHA afterwards, per the ADR-0029 mutation policy.
3. Draw the run-order assignments with the recorded seed.
4. For each run: apply §4 controls, run the task under the assigned condition
   within its budget, capture `run.json` and raw artifacts.
5. Score per §6, aggregate per §7, and write `ANALYSIS.md` plus the #190
   decision record.

## 10. Limitations and non-goals

- Ten paired tasks cannot establish general product improvement; conclusions
  are scoped to the measured task classes.
- Efficiency gains are secondary evidence; they never compensate for a
  correctness regression.
- Provider-unavailable Chakra runs measure the honest-fallback path, not
  precise enrichment; both are reportable and must not be pooled without
  labeling.
