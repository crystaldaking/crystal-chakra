## Corrections and evidence

The initial `Ready` response with no callers was a readiness defect.
A longer raw-LSP probe obtained the correct caller about 87 seconds after
startup, once import and indexing completed. The Kotlin hook now retries
null hierarchy preparation under a separate 180-second readiness budget.
It waits through the owned session, checks cancellation and shutdown, and
uses the same deadline for hierarchy preparation and relation requests.
A short caller wait can return `catching_up` while the owner finishes;
explicit operation cancellation/deadlines still stop the work. Document
changes invalidate the previous synchronization proof. Warm queries keep
their normal request budget. A prepared item with no callers is valid;
a null preparation response cannot publish a false ready result.

An Android raw-LSP probe exposed a second readiness defect. At 90.2 seconds,
incoming calls still included both overloads. At 103.4 seconds both import
and indexing progress tokens ended; a fresh query at 104.62 seconds returned
only the correct `caller(Context)`. Definitions and references also became
unambiguous. The Kotlin hook now requires an idle work-done epoch and rejects
queries spanning new work. The worker retains at most 64 active tokens of
256 bytes, with safe timeout after overflow or missing completion. Logs:
`android-probe.log` and `android-probe-before-progress.log`.

The offline metadata classifier also had a Kotlin routing defect: it called
the Kotlin classifier without loading the shared JVM project model. Kotlin
now loads Gradle/Maven metadata, with regression tests for module boundaries,
Android test variants, and KMP test source sets. Parser regressions cover
`expect`/`actual`, Android annotations, and native platform imports. These
checks do not imply compiler-level resolution of platform symbols.

The Docker tests use official kotlin-server 263.4702.0, Maven 3.9.16,
Gradle 8.14.3, Kotlin plugin 2.2.20, JDK 21, AGP 8.11.1, Android SDK
platform 35 and build tools 35.0.0. Downloaded distributions have pinned
checksums. Gradle and Maven dependency caches use Docker named volumes.
Offline Chakra indexing never invokes this build tooling; the external
precise server can execute project import and download dependencies.

The independent dependency audit blocker was fixed by updating only the
locked `rustls` version from 0.23.44 to 0.23.45. The repeated `cargo deny
check` passes. That audit-only change added no dependency; the later import implementation
below reuses workspace-managed `tempfile` and Unix `nix`.

## Acceptance protocol

The initial real-provider target contained four separate ignored tests;
subsequent follow-ups added mixed Kotlin/Java and standalone-script fallback.
Every positive project scenario must return the expected incoming caller at revision 1, the new
caller after an edit at revision 2, and an outgoing target at revision 2,
all with `KotlinLsp` provenance. The test uses the default one-second caller
wait and retries only `catching_up`, under one ten-minute operation deadline
per phase for cold downloads/indexing under emulation. A `Ready` result with
missing relations fails immediately; the helper never retries it into a pass.

- Maven and Gradle JVM: conventional Kotlin projects.
- Android: an Android library with SDK type `android.content.Context`;
  the incoming result must distinguish its overload from an `Int` overload.
- Multiplatform: common `expect` declaration and JVM/JS/Linux Native
  `actual` implementations; a common function's callers must include the
  consumers from all three platform source sets.

Reproduce from the repository root:

```sh
./tools/run_lsp_tests.sh -p chakra-provider-kotlin-lsp --test real_provider -- --ignored --test-threads=1 --nocapture
```

A failed assertion is a release gate. Successful syntax or hermetic tests
cannot substitute for these real-server assertions. iOS SDK integration,
Compose compiler plugins, arbitrary custom source-set graphs, and every
Kotlin/Gradle/AGP version combination require additional evidence; this
fixture matrix is a bounded support contract, not universal compatibility.

## Direct KMP diagnosis

Two fresh raw-LSP runs bypassed Chakra entirely. Both used the same pinned
ILS-263.4702.0 server and the common/JVM/JS/Linux Native fixture above, with
server indexes on the container filesystem. The first run omitted the
fixture's Gradle memory/worker settings; the second restored the exact
`org.gradle.jvmargs=-Xmx512m` and `org.gradle.workers.max=2` settings.
The second run exported the imported model using the server's advertised
`workspace/executeCommand` command `exportWorkspace`.

The client waited for `intellij/workspaceImportState` to report `FINISHED`
with `SUCCESS`, and for both Importing and Indexing progress tokens to end,
before making semantic requests. Those conditions held at 108.02 seconds
in the first run and 146.11 seconds in the second. The latter then returned:

| Request | Observed result |
| --- | --- |
| `prepareCallHierarchy` on common `target` | `null`, in 4.527 s |
| `documentSymbol` on common file | Both `target` and `caller` |
| `references` on common `target` | Only the call in the same file |
| Definition of common `platformName()` | Empty list |
| `prepareCallHierarchy` on JVM, JS, Native callers | `null`, each in under 0.7 s |
| Definition of platform calls to `target()` | Empty lists |
| Common preparation after explicitly opening all five files | Still `null`, in 0.134 s |
| `workspace/symbol` for `platformName` | Empty list |

The exported workspace contains exactly three modules: `sample`,
`sample.jvmMain`, and `sample.jvmTest`. All three have **zero source roots**.
For example, `sample.jvmMain` has the content directory
`/tmp/kmp-probe/src/jvmMain`, but no registered `src/jvmMain/kotlin` source
root. There are no common, JS or Native modules, and no Kotlin settings.
The two imported libraries are JVM Kotlin stdlib and JetBrains annotations.
A successful import notification therefore does not mean that the KMP
source-set graph has been imported.

Bytecode inspection of the installed
`language-server.workspace-import.gradle-plugin.jar` confirms the relevant
implementation, independently of upstream `main`: `ModuleSourceSetsModelBuilder`
reads Java `SourceSetContainer` and Android source sets;
`GradleSourceSetRootResolver` obtains roots through `SourceSet.getAllJava()`
and optional IDEA source directories. `KotlinExtensionReflection.getTarget()`
uses the singular Kotlin `getTarget` accessor for friend compilations.
The inspected builder has no traversal of KMP's targets/source-set graph.

An independent Gradle task printed both views of the unchanged fixture.
Java `SourceSetContainer` contains only `jvmMain` and `jvmTest`, whose
`allJava.srcDirs` point to the absent `src/jvmMain/java` and
`src/jvmTest/java` directories. Kotlin's own `sourceSets` contains the
actual Kotlin directories and `dependsOn` relationships, including the
intermediate `webMain`, `nativeMain` and `linuxMain` source sets. Kotlin
targets are `js`, `jvm`, `linuxX64`, and `metadata`. This confirms that
Gradle has the required graph, while the importer reads the Java view
that does not expose it. The diagnostic Gradle task passed in 14 seconds;
its init script and output are `dump-source-sets.gradle` and
`gradle-source-sets.log` in the local evidence directory.

This localizes the demonstrated failure to incomplete project import in
the pinned server. It is reproducible without Chakra's worker, and opening
all documents does not repair it. The 600-second acceptance failure is an
aggregate deadline for repeated attempts to obtain a usable hierarchy;
it is not a single LSP request taking 600 seconds. The short null responses
after completed import explain why increasing that deadline cannot restore
the missing project model.

A controlled third run supplied the exported model through the server's
JSON importer, adding only `src/commonMain/kotlin` and `src/jvmMain/kotlin`
as source roots of `sample.jvmMain`. The temporary copy's Gradle entry
files were renamed to select the JSON importer; Kotlin sources, server,
libraries and SDK were unchanged. The server reported JSON import success
and idle indexing at 91.51 seconds. Common hierarchy preparation now returned
`target()` in 2.869 seconds, and incoming calls returned exactly `caller()`
and `jvmCaller()` in 0.823 seconds. The JVM caller's outgoing query also
resolved the common target. JS and Native preparation remained null.

This is a diagnostic control, not an acceptable KMP workaround. Flattening
common and JVM into one module produced `OVERLOAD_RESOLUTION_AMBIGUITY`,
`NOT_A_MULTIPLATFORM_COMPILATION`, and `EXPECT_AND_ACTUAL_IN_THE_SAME_MODULE`
diagnostics. The common target's outgoing call to `platformName()` remained
unresolved. Restoring source roots removes the immediate null-hierarchy
failure, but correct KMP support also needs target-aware modules,
dependencies, compiler settings, and `expect`/`actual` relationships.
The control does not establish that the pinned server can support all
targets after those missing inputs are supplied; that remains to be tested.

Local evidence is under `target/kmp-diagnosis/`: `probe.py`, `probe.log`,
`wire.jsonl`, `results.json`, and `server.log` for the first run;
`probe-export.py` and `export/{probe.log,wire.jsonl,results.json,server.log,workspace.json}`
for the second; and `pinned-importer-bytecode.txt` plus
`pinned-root-resolver-bytecode.txt`. Assertions over the captured JSON
verified the three module names, zero source roots, all five null hierarchy
responses, and the lack of cross-file symbols. No runtime code or acceptance

The control is recorded in `probe-root-mapping.py` and

## Review boundaries

Self-review and architecture review checked the provider-worker boundary,
atomic revision publication, delta synchronization, provenance, bounded
waiting, cancellation and process ownership. The readiness rule is local
to Kotlin; the shared worker provides observations without imposing Kotlin
policy on other languages. No domain/MCP contract, snapshot semantics or
repository-wide reindex path was added. ADR-0056 records the decision.

The required KMP real-server gate remains a release blocker until the same
common/JVM/JS/Native fixture passes. Syntax candidates cannot be relabeled
as compiler-precise facts to satisfy it. Replacing or extending the provider
must first prove target-aware project import and cross-source-set semantics;
increasing timeouts alone is not evidence of that support.

Existing staged documentation was preserved byte-for-byte. The changes
remain uncommitted on the validation branch. This work has not created
GitHub issues, pushed branches, tagged or published a release.

The release workflow now includes `language-acceptance`, which runs
`tools/run_lsp_tests.sh`; `publish` depends on its success. The wrapper
runs the ordinary workspace suite and each real provider, continues after
failures to collect the full result, and returns a failing exit status.
This makes the KMP failure an explicit publication gate. The workflow has
not been dispatched to GitHub in this task.


## Follow-up 2026-09-18: confirmed KMP query strategy

A target-aware JSON model with separate common/JVM/JS/Native source sets,
Kotlin compiler settings, platform libraries, direct `dependsOn` settings,
and exported transitive source-set module dependencies restores semantic
resolution. The raw-server probe resolves all four incoming references and
all three `actual` implementations. Deliberately changing each platform's
`target()` call to `target(123)` produces `TOO_MANY_ARGUMENTS`; restoring the
source clears it. Empty diagnostics therefore are not the only evidence
that JS and Native analysis works.

The remaining call-hierarchy defect is in the pinned renderer, whose
parameter presentation requires `toLightMethods(...).firstOrNull()`.
JS/Native functions have valid definitions and references but no rendered
hierarchy item. A Kotlin-specific Chakra strategy now uses syntax to locate
actual call expressions/owners and requires a unique LSP definition to
confirm each relation. It never derives precise bindings from names alone.
The model directory must be separate from the Gradle root, otherwise the
server selects Gradle import and overwrites the model. The worker's optional
initialization-root hook preserves canonical source URIs and cwd.

The actual Chakra real-provider test passed in Docker with this prepared
model. The first run took 68.44 seconds to import/query and 0.81 seconds to
observe the edit. An expanded repeat took 68.19 seconds initially and 0.93
seconds after the edit. It additionally verifies:

- Four incoming callers from common/JVM/JS/Native, then five at revision 2.
- Platform callers of the `Int` overload are excluded from the zero-argument
  target's incoming relations.
- Separate outgoing queries for JVM, JS, and Native callers resolve the
  correct common declaration, with `KotlinLsp` provenance and no truncation.
- The common target's outgoing call resolves the common `expect` declaration.
- The added caller's outgoing query still passes after the revision change.

Artifacts: `target/kmp-fix/chakra-kmp-template.log`,
`chakra-kmp-expanded.log`, `model-v3/`, and `model-v5/`. These runs use the
explicit diagnostic environment variable `CHAKRA_TEST_KOTLIN_MODEL_TEMPLATE`;
the default acceptance command does not use it. **This is evidence for the
query strategy, not completion of automatic KMP support.** Production model
preparation, build-input invalidation, and the unmodified default four-project
acceptance gate remain required.

Current focused validation: 39 tests passed across `chakra-language-kotlin`,
`chakra-provider-kotlin-lsp`, and `chakra-provider-worker` (four real-provider
tests ignored by the ordinary suite). Four new query tests cover duplicate
references, callable values, wrong/ambiguous definitions, UTF-16 positions,
immutable-source queries, cancellation, and readiness. A new lifecycle test
verifies external import roots with canonical source URIs. Focused clippy
with warnings denied and `git diff --check` pass. Earlier full-workspace
results above predate this strategy and must be rerun before release.


For automatic preparation, a diagnostic Gradle task successfully exercised
KGP 2.2.20's `IdeMultiplatformImport.instance(project)`,
`addDependencyOnResolvers(task)`, and `resolveDependencies(sourceSet)`.
Unlike the earlier Java source-set view, it supplies all 14 production/test
source sets, transitive `DependsOn` and `Friend` source dependencies,
transformed common metadata libraries, JVM/JS artifacts, and Native platform
libraries (including POSIX). The task completed in 16 seconds with cached

bounded `CatchingUp`. These cases have hermetic lifecycle regressions.

The owner bounds Gradle preparation by the startup/operation deadline,
checks cancellation, caps retained model/log sizes, and terminates its
process group on exit. Temporary models are replaced on restart and removed
with their owner. Subsequent hardening compares captured build-input metadata
before/after preparation and around queries; a mismatch reports
`CatchingUp`, never a model attributed to an older revision. Queries outside
imported KMP source roots retain fallback. Focused tests cover stale inputs
both before and during preparation, canonical-root rejection, process-group
cancellation, timeout, and suppression of raw build output from public errors.

The four-project run above precedes this last metadata/root hardening.

166.11 seconds, the source edit took 1.73 seconds, and regeneration after a
build/source-root change took 113.34 seconds and returned all six callers.

The preliminary `fmt`, workspace Clippy/tests, `cargo deny`, and diff checks
