# v0.1.1 rust-analyzer readiness evaluation

Date: 2026-08-18

## Baseline

The earlier pinned Zed run at commit
`bc538def4545534201bbfcac4e95ac34ea6501b6` retained 1,929 Rust files and
55,346,203 bytes of source. Syntax indexing was independently useful while
rust-analyzer remained `catching_up`; a precise `callers` attempt waited about
4.34 seconds before honestly returning syntax candidates. The former provider
contract could send every retained source body on first use and held a
count-only 128-entry cache.

The public corpus was not available in this worktree for a new real-provider
run. The regression below fixes the same file/byte scale hermetically so the
transport and memory claims remain repeatable without a global rust-analyzer.

## Interpretation

- Syntax readiness does not wait for provider readiness. A provider timeout
  returns `catching_up`, stage/source, and syntax fallback within its explicit
  budget.
- First-use provider traffic now scales with the selected target source rather
  than total workspace text.
- An ordinary one-file revision compares one replaced source allocation and
  sends one watched-file event when that document is disk-backed.
- Cache memory is bounded independently by entry count and estimated retained
  bytes; status exposes current/cumulative evidence.
- No result is accepted merely because it carries the requested revision: the
  engine must still publish the same fresh revision after enrichment.
