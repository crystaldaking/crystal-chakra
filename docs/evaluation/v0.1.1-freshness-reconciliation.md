# v0.1.1 freshness reconciliation evaluation

Date: 2026-08-18
Issue: [#17](https://github.com/crystaldaking/crystal-chakra/issues/17)

## Purpose

Measure the cost of deterministic `RequireFresh` after replacing two complete
body scans with one cached content snapshot and explicit Git/inode consistency
checks. The measurement must preserve immediate read-your-writes and cannot use
watcher silence as freshness evidence.

## Corpus and command

The corpus is the local `psp-app` Git worktree previously used to establish the
v0.1.1 baseline. The opt-in test indexes the repository once, starts the live
owner, then executes ten warmed `symbol_search` requests with
`RequireFresh`:

```text
CHAKRA_LARGE_REPOSITORY=/Users/crystal/Projects/psp-app \
  cargo test --release -p chakra-language --test large_workspace \
  large_repository_warmed_noop_freshness_is_bounded \
  -- --ignored --nocapture --test-threads=1
```

The test also asserts that each request performs exactly two Git inventory
checkpoints, reads no source body, publishes no full reconciliation, and
returns a fresh non-empty result.

## Result

| Measurement | v0.1.0 baseline | v0.1.1 result |
| --- | ---: | ---: |
| Fresh `symbol_search` | 91.7–98.8 ms | 23.898–26.217 ms |
| Median | not recorded | 25.690 ms |
| Samples | not recorded | 10 |
| Git subprocesses | not instrumented | 20 total / 2 per query |
| Files inspected | two full body scans | 23,160 identity observations |
| Source bytes represented by inspections | not instrumented | 151,371,880 bytes |
| Source bodies read | all admitted bodies twice | 0 |
| Source bytes read | all admitted bytes twice | 0 |

The measured speedup is 3.5–4.1×, below the preferred 5× target in #17. The
remaining approximately 24–26 ms is the cost of two Git inventory subprocesses
and two filesystem identity passes over 1,158 admitted sources.

## Correctness budget decision

The preferred target is not met by removing either identity pass. One pass
captures the candidate state; the other proves that no file changed while the
snapshot was assembled. A watcher epoch cannot replace that proof because an
edit followed immediately by a query may reach the filesystem before its
notification reaches user space.

For v0.1.1, a release-mode warmed budget of 27 ms on this corpus is therefore
accepted under #17's documented-correctness alternative. Issue #21 may reduce
the wall-clock portion through bounded parallel identity inspection, but it
must retain the same observations and zero-body-read assertions.

## Deterministic regressions

- Immediate edit followed by a fresh query exposes the new symbol atomically.
- Same-size source replacement with restored mtime is detected through the
  stronger identity and reparses one file.
- Atomic save, create, rename, delete, temporary syntax error, and rapid
  editor-style replacement converge without caller sleeps.
- Watcher degradation, error, dropped-event, reordered/non-contiguous epoch,
  uncertain-hint, and periodic checkpoint policy force a full reconciliation.
- Concurrent barrier generations are completed only when covered by the same
  verified snapshot.
- A clean `diff_context` retains its second revision-pin barrier but performs
  two lightweight no-op proofs: four Git inventory subprocesses, zero body
  reads, zero reparses, and zero full reconciliations.
