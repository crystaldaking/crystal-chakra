# Chakra v0.1 — Minimum Useful Product

Status: implementation scope authority

Historical scope note: the original implementation pack was intentionally
Rust-only and deferred PHP. PHP was promoted into this release by a later
explicit product decision recorded in ADR-008. This roadmap describes the
resulting v0.1 release scope rather than rewriting that history.

This file remains the baseline scope and architectural constraint for the
v0.1 release line; it is not a claim that every v0.1.x milestone is still the
original Rust/PHP implementation slice. After v0.1.0, an accepted GitHub
milestone plus its ADRs and issue acceptance criteria is the scope authority
for that minor/patch release. Such work may add first-class languages or
provider adapters while preserving the deferred boundaries below. A milestone
cannot silently authorize persistence, multi-worktree orchestration,
cross-repository graphs, embeddings, distributed indexing, or a web UI.

## 1. Goal

v0.1 must prove one thing:

> A live, structured, provenance-aware code intelligence service can make an AI coding agent materially better at understanding Rust and PHP repositories than ordinary text search/read alone.

Do not attempt to finish the entire Chakra architecture in v0.1.

## 2. Supported environment

v0.1 supports:

- Rust and PHP repositories, including repositories containing both languages;
- one registered repository;
- one active materialized worktree;
- local execution;
- one Chakra daemon/process model sufficient for real MCP use;
- Tree-sitter syntax intelligence;
- optional/on-demand rust-analyzer enrichment for Rust;
- Git diff awareness;
- live filesystem updates;
- in-memory query graph/index;
- no persistent graph snapshot restoration requirement.

## 3. Required queries/tools

v0.1 must expose a coherent structured contract for:

1. `status`
2. `repo_map`
3. `search`
4. `symbol_search`
5. `context`
6. `callers`
7. `diff_context`

Additional tiny support queries are acceptable when necessary, but do not expand into the full future MCP catalog.

## 4. Required fact quality model

Every relevant result must preserve:

- provenance;
- precision (`precise`, `syntax`, `heuristic`, `textual` or final equivalent);
- workspace revision;
- freshness/state metadata where relevant.

A text match must never masquerade as a precise reference.
A syntax call candidate must never masquerade as a precise language-provider call.

## 5. Required live update behavior

After Chakra is ready:

1. edit a Rust or PHP source file;
2. immediately request a fresh `context` or `diff_context`;
3. Chakra must reflect the latest file state without requiring the client to sleep.

At minimum, syntax-level read-your-writes must be deterministic.

If rust-analyzer has not processed the corresponding current state, Chakra must not return stale precise data as current. It may wait on a bounded provider barrier or return current syntax data with provider state `catching_up`/equivalent.

## 6. Revision publication

v0.1 must implement atomic query-visible revisions from the beginning.

No query may observe a half-updated symbol graph during a file refresh.

This is not deferred because retrofitting it later would distort the engine architecture.

## 7. Rust and PHP syntax layers

Use the official Tree-sitter Rust and PHP grammars to index the information required for useful `repo_map`, `symbol_search`, `context`, `callers`, and `diff_context` behavior. Keep parsing and syntax extraction in separate language adapters and combine only language-neutral graph facts.

Likely facts include:

- functions;
- methods;
- structs;
- PHP classes and interfaces;
- traits;
- PHP namespaces and properties;
- impl blocks;
- modules;
- imports/use declarations;
- source ranges;
- syntax call candidates;
- basic test identification.

Do not build a Rust or PHP type checker. PHP v0.1 support is syntax-tier; no PHP language server is required. Query responses must carry the symbol language, and rust-analyzer must never be invoked for a PHP symbol.

## 8. rust-analyzer enrichment

rust-analyzer is a live provider for semantic enrichment.

v0.1 should integrate only the precise capabilities needed to improve the selected queries.

Do not crawl every symbol through LSP to build a complete precise graph.

Prefer lazy/on-demand enrichment:

```text
syntax graph/index
+
precise result fetched for the user query
+
revision-scoped cache if useful
```

Track enough document/provider state to avoid falsely fresh precise results.

## 9. Git diff

`diff_context` must understand the current materialized repository state sufficiently to identify:

- modified files;
- staged/unstaged changes as needed by the chosen default scope;
- untracked Rust and PHP files when relevant;
- deleted/renamed files where feasible;
- changed syntax symbols;
- related callers/tests available from the current graph/provider data.

Document exact diff scope semantics.

## 10. Filesystem watching

Use a production-appropriate watcher crate selected during discovery.

Required properties:

- debounce/coalescing;
- bounded event pipeline;
- editor atomic-save tolerance;
- content/state reconciliation;
- ignored/generated path exclusions;
- no whole-repository reindex for a normal single-file edit.

## 11. Repository scan scope

Default indexed files:

- Git-tracked Rust/PHP project files;
- untracked non-ignored Rust/PHP project files needed for live agent edits.

Respect `.gitignore` by default.

Do not index `target/` or `.git/` as source.

## 12. In-memory state

v0.1 does not require persistent graph recovery.

Startup may rebuild the syntax graph deterministically.

Measure startup/index cost before designing snapshot persistence.

SQLite may be omitted entirely from the first useful slice unless clearly needed for repository configuration or other non-graph state.

## 13. MCP transport

Choose the smallest transport/configuration that lets at least Codex connect to a real running v0.1 service.

Do not implement both a daemon HTTP server and stdio bridge solely because the north-star spec mentions both.

During Phase 0, verify current Codex MCP transport support and choose one path.

Transport concerns must remain outside the query/domain layer.

## 14. Workspace / crate structure

Use a Cargo workspace only where the boundaries provide immediate value.

Recommended initial crates:

```text
crates/
  chakra-domain/
  chakra-engine/
  chakra-language/
  chakra-language-php/
  chakra-language-rust/
  chakra-mcp/
  chakra-cli/
```

A separate `chakra-graph`, `chakra-git`, or other crate may be introduced when its boundary is already meaningful. Do not create empty future crates.

The user-facing binary is always `chakra`.

## 15. Required Git workflow during implementation

The implementation repository must be initialized with Git before substantive code is written.

Initial repository governance files (`AGENTS.md`, project skills, SPEC, v0.1 roadmap) should be committed early so subsequent implementation commits are governed by them.

Before every commit, follow the mandatory skill workflow from `AGENTS.md`:

1. `$chakra-self-review`
2. `$chakra-architecture-review` when triggered
3. `$chakra-validate`
4. staged patch inspection
5. `$chakra-commit`

No Git hooks are required.

## 16. Required v0.1 regression tests

### Atomic revision

Concurrent/repeated queries during update must see old or new revision, never hybrid state.

### Immediate fresh read

Edit a file and immediately request current context. Latest syntax state must be visible without arbitrary sleep.

### No full reindex

A normal single-file edit must update only the affected indexing state. Test using instrumentation/observable counters rather than timing alone.

### Rename/delete

Renamed/deleted symbols/files must not leave ghost query results.

### Syntax error

A temporarily broken Rust or PHP file must not crash Chakra or corrupt the rest of the repository state.

### rust-analyzer stale barrier

A precise result must not be labeled current for an older provider/document version after the file has changed.

### diff_context

A fixture change must yield changed symbol(s) and at least the related syntax/provider facts Chakra claims to support.

## 17. Example fixture

Create small realistic Rust and PHP fixtures, for example:

```text
api/refund.rs
    → PaymentService::refund
        → Provider::refund

traits / impls
related tests
```

Use it for integration and MCP contract tests.

## 18. Performance measurements

Record at least:

- initial Rust and PHP syntax indexing time for fixture(s);
- single-file reindex time;
- `symbol_search` latency;
- `context` latency;
- `diff_context` latency;
- rust-analyzer enrichment latency when applicable.

Do not build persistence solely to improve an unmeasured startup time.

## 19. v0.1 definition of done

v0.1 is ready for product evaluation when all are true:

- `chakra` builds on the pinned Rust toolchain;
- agent can connect through MCP;
- repository indexes successfully;
- required queries return typed/structured results;
- provenance/precision are visible;
- file edits are reflected incrementally;
- fresh syntax queries are read-your-writes;
- precise stale-provider data is not mislabeled current;
- `diff_context` is useful on the Rust and PHP fixtures;
- atomic revision regression test passes;
- validation gates pass;
- README documents how to run Chakra and connect an agent;
- Git history contains focused reviewed commits.

## 20. Explicitly not v0.1

Do not implement unless the scope document is intentionally amended:

- multi-worktree support;
- language provider pools/resource eviction;
- historical commit materialization;
- commit snapshot persistence/reuse;
- SQLite graph restoration;
- SCIP;
- semantic embeddings;
- cross-repository graph;
- complete precise call graph;
- generic full `impact` query;
- `history` query;
- web UI;
- distributed architecture;
- Jira/Slack/log integrations.

## 21. Product validation after v0.1

Run real agent tasks with and without Chakra.

Create an evaluation note capturing at least:

- task descriptions;
- tool/search/read call counts when observable;
- context/token overhead when observable;
- files/tests discovered;
- task outcome;
- stale-context incidents;
- qualitative usefulness of Chakra tools.

Only then prioritize v0.2+.
